## 1. 项目重新定位

### 1.1 核心问题诊断

当前项目存在三个名称（SmartCampus、智评AI、智界·灵动校园），对应的定位也在"智慧校园管理系统""AI健康使用系统""AI科普平台"之间摇摆。这种模糊性直接导致了功能堆砌——什么都想做，结果什么都不够深入。

判断一个校园产品的定位是否清晰，可以问一个问题：**校长/教务主任/班主任第一次打开系统时，最先用的三个功能是什么？** 如果答案超过五个，说明定位已经失焦。

### 1.2 统一品牌与定位

| 项目 | 决策 | 理由 |
|------|------|------|
| 统一名称 | **智评校园**（SmartCampus 保留为英文代号） | "智评"二字既包含"智能评估"的技术属性，也承载"智慧校园"的场景属性，比"灵动校园"更有辨识度，比"智评AI"更完整 |
| 产品定位 | **以教学质量评估为核心的智慧校园管理平台** | 避开与大厂通用校园系统的正面竞争，从"教学评估"这个差异化切入点切入，再逐步扩展到校园管理的其他模块 |
| 核心价值主张 | 用数据和AI帮助学校"看清"教学效果，让每一位老师的教学成长可量化、可追踪 | 这是当前通用校园系统普遍做不好、而AI又能真正发挥价值的领域 |

### 1.3 目标用户与应用场景

**主要用户分层：**

- **决策层（校长/教务主任）**：看教学质量全貌、教师能力画像、学生成长趋势
- **执行层（教师/班主任）**：教学任务管理、学生学情分析、班级事务处理
- **参与层（学生/家长）**：学习记录、成长档案、校园服务使用

**核心场景：**

1. 期末考试后，教务主任需要快速了解各年级、各班级、各学科的教学质量分布，找出薄弱环节
2. 教师备课时，系统基于班级学情数据推荐教学重点和分层作业
3. 学生查看自己的成长档案，不仅有成绩，还有技能发展、心理健康、荣誉记录的完整画像

## 2. 需求分析与功能规划

### 2.1 现有功能梳理

对现有9大功能模块做"留合砍"处理：

| 模块 | 处理方式 | 说明 |
|------|----------|------|
| 用户管理 | **保留并增强** | 三角色体系是基础，需细化权限粒度 |
| 课程管理 | **保留核心** | 保留课程CRUD和课表，选课功能降为P2 |
| 校园服务 | **部分保留** | 教室预约、报修保留；图书借阅、设备预约、食堂订餐砍掉 |
| 活动管理 | **降级为P2** | 功能完整但非核心，延后优化 |
| 通知系统 | **保留并增强** | 是系统触达用户的核心通道，需完善 |
| 成长档案 | **升级为核心** | 这是差异化竞争力的关键模块，需深度建设 |
| AI学习助手 | **合并** | 与成长档案的学情分析合并 |
| AI写作助手 | **砍掉** | 与校园核心场景关联弱 |
| AI情感分析 | **合并** | 融入成长档案的心理健康模块 |
| AI科普乐园 | **砍掉** | 纯娱乐属性，偏离核心定位 |
| AI智能识别(OCR) | **保留并增强** | 与成绩录入、作业批改深度结合 |
| AI创意工具 | **砍掉** | 与校园核心场景无关 |
| AI健康 | **砍掉** | 偏离核心定位，作为独立产品方向更合适 |
| 数据可视化 | **保留并重构** | 围绕教学评估场景重新设计仪表盘 |
| 移动端 | **暂停** | 集中资源做好Web端 |

### 2.2 功能优先级规划

#### P0 — MVP 核心（必须有，否则产品不成立）

**1. 教学质量评估中心**
- 核心价值：让学校管理者一眼看清教学质量全貌
- 用户故事：
  - 教务主任导入考试成绩后，系统自动生成年级/班级/学科的多维度质量分析报告
  - 教师可以查看自己所教班级的成绩分布、知识点掌握情况、与平行班的对比
  - 系统自动识别薄弱班级和薄弱知识点，给出预警

**2. 学生成长档案**
- 核心价值：从"唯分数论"转向"全面成长记录"
- 用户故事：
  - 学生/家长可以查看包含成绩、技能、荣誉、心理健康的完整成长档案
  - 教师可以为学生添加技能评价和荣誉记录
  - 成长档案支持按学期/学年的趋势分析和导出

**3. 用户与权限体系**
- 核心价值：三角色分级权限，数据按角色隔离
- 关键能力：JWT认证、角色权限矩阵、班级/学科数据范围控制

#### P1 — V1.0 完善（核心体验闭环）

**4. 课程与课表管理**
- 课表编排、教师任课分配、课程信息维护

**5. 校园服务（精简版）**
- 教室预约：教师预约公共教室（多媒体室、实验室等）
- 报修管理：师生提交报修，后勤处理跟踪

**6. 通知与消息系统**
- 系统通知、紧急通知、WebSocket实时推送
- 通知按角色/班级/年级定向发送

**7. AI 学情分析**
- 基于成绩数据的知识点掌握度分析
- 学生个人学情报告与学习建议
- 班级教学效果诊断

#### P2 — V2.0 扩展（锦上添花）

**8. 活动管理**
- 活动发布、报名、兴趣小组

**9. 选课系统**
- 选修课/社团课的选课管理

**10. AI 作业批改（OCR + 智能评分）**
- 纸质作业/试卷扫描录入
- 客观题自动批改，主观题辅助评分

**11. 心理健康测评与跟踪**
- 定期心理测评问卷
- 情绪趋势跟踪与预警

## 3. 架构重构方案

### 3.1 后端架构重构

#### 当前问题

- 业务逻辑直接写在路由处理函数中，缺少服务层
- 32个JS文件按模块组织，但分层不清晰
- 没有统一的错误处理、参数校验、响应格式

#### 目标架构：经典三层架构

```
backend-api/src/
├── config/              # 配置文件
│   ├── database.js      # 数据库连接
│   ├── jwt.js           # JWT配置
│   └── index.js         # 环境变量汇总
├── middleware/          # 中间件
│   ├── auth.js          # 认证中间件
│   ├── permission.js    # 权限中间件
│   ├── errorHandler.js  # 统一错误处理
│   └── validator.js     # 参数校验
├── models/              # 数据模型层（轻量ORM封装）
│   ├── user.model.js
│   ├── course.model.js
│   └── ...
├── services/            # 业务逻辑层（核心层）
│   ├── auth.service.js
│   ├── teaching.service.js    # 教学质量评估
│   ├── portfolio.service.js   # 成长档案
│   ├── ai.service.js          # AI能力统一封装
│   └── ...
├── routes/              # 路由层（只做参数接收和响应返回）
│   ├── auth.routes.js
│   ├── teaching.routes.js
│   ├── portfolio.routes.js
│   └── ...
├── utils/               # 工具函数
│   ├── response.js      # 统一响应格式
│   ├── asyncHandler.js  # 异步错误捕获
│   └── ...
├── websockets/          # WebSocket 处理
│   └── socketHandler.js
└── app.js               # 应用入口
```

#### 重构原则

1. **路由层只做三件事**：接收参数、调用service、返回响应。不包含任何业务逻辑
2. **服务层是业务逻辑的唯一归属**：可被多个路由复用，便于单元测试
3. **模型层做数据访问封装**：SQL写在model中，service不直接拼SQL
4. **中间件处理横切关注点**：认证、权限、日志、错误处理统一处理

#### 统一响应格式

```javascript
// 成功响应
{
  code: 0,
  data: { ... },
  message: "success"
}

// 失败响应
{
  code: 40001,  // 错误码：4xxxx用户错误，5xxxx系统错误
  data: null,
  message: "参数校验失败"
}
```

#### 关键改进

1. **引入 Pinia 做状态管理**：替代散落在各组件的data共享，用户信息、全局配置集中管理
2. **API层统一封装**：所有请求走 `api/` 目录，拦截器统一处理token、错误码、loading
3. **组件分层**：通用组件（DataTable、SearchForm等）抽象出来，减少页面重复代码
4. **组合式函数复用逻辑**：表格分页、表单提交、文件上传等通用逻辑用 composables 复用
5. **路由按角色拆分**：管理员、教师、学生三套路由，按角色动态加载

### 3.3 数据库优化

#### 当前问题

- 约30张表，部分表只有表结构没有对应业务
- 索引设计不系统
- 缺少统一的命名规范

#### 表结构优化方案

**保留并增强的核心表（P0/P1）：**

| 表名 | 优化点 |
|------|--------|
| users | 增加 `role` 字段索引，补充 `last_login_time`、`status` |
| courses | 增加 `course_code` 唯一索引，关联学科表 |
| classes | 班级表，关联年级、班主任 |
| subjects | 学科表（新增），统一学科字典 |
| exams | 考试表（新增），考试名称、时间、年级、学期 |
| exam_scores | 成绩表（增强），关联考试、学生、学科，增加分数段标记 |
| teaching_quality_stats | 教学质量统计表（新增），预聚合的班级/学科质量数据 |
| student_portfolios | 成长档案主表（增强） |
| portfolio_skills | 技能记录（增强） |
| portfolio_honors | 荣誉记录（保留） |
| mental_health_records | 心理健康记录（保留） |
| classrooms | 教室表（保留） |
| classroom_reservations | 教室预约表（保留） |
| repairs | 报修表（保留） |
| notifications | 通知表（保留） |
| notification_reads | 通知已读表（新增，精确追踪已读状态） |

**建议删除的表（P2以后再考虑）：**

- `books` / `book_borrows` — 图书借阅，砍掉
- `equipment` / `equipment_reservations` — 设备预约，砍掉
- `canteen_menus` / `canteen_orders` / `canteen_traffic` — 食堂相关，砍掉
- `activities` / `activity_signups` / `interest_groups` — 活动相关，降级到P2
- `ai_chat_history` — 通用AI对话记录，砍掉
- `ai_writing` — AI写作，砍掉
- `ai_science` — AI科普，砍掉
- `ai_health_records` — AI健康，砍掉

#### 索引设计原则

1. **主键索引**：所有表必须有自增主键 `id`
2. **外键查询索引**：凡是 WHERE 条件中出现的关联字段（user_id、class_id、course_id等），一律建索引
3. **联合索引**：针对高频查询场景建联合索引，注意区分度高的字段放前面
   - 例如：`exam_scores` 建 `(exam_id, subject_id, student_id)` 联合索引
4. **时间范围查询**：有时间范围筛选的字段（created_at、exam_time等）建索引

#### 命名规范

- 表名：小写 + 下划线，复数形式（如 `exam_scores`、`notifications`）
- 字段：小写 + 下划线
- 主键：统一叫 `id`
- 外键：`{关联表单数}_id`（如 `user_id`、`class_id`）
- 时间字段：`created_at`、`updated_at`，统一 DATETIME 类型
- 状态字段：`status`，TINYINT 类型，0=禁用，1=启用（或根据业务定义）

## 4. AI 功能重新设计

### 4.1 设计原则

当前7-8个AI模块本质上都是"DeepSeek API换壳"——用户输入一段话，大模型返回一段话，与校园场景没有深度绑定。这样的AI功能没有壁垒，也没有用户粘性。

AI功能要产生真正的价值，必须遵循三个原则：

1. **场景内嵌**：AI不是一个独立模块，而是嵌入在教学评估、成长档案、作业批改等具体场景中
2. **数据驱动**：AI输出必须基于学校的真实数据（成绩、学情、学生档案），而不是通用对话
3. **减轻负担**：AI的核心价值是帮老师"省时间"，而不是给学生增加一个聊天玩具

### 4.2 核心AI应用场景设计

#### 场景一：智能学情分析（P1）

**位置**：教学质量评估模块 → 班级/学生学情详情页

**功能描述**：

系统不是简单地展示成绩排名，而是用AI分析成绩背后的原因，给出可操作的建议。

**具体能力**：

1. **班级学情诊断报告**
   - 输入：一次考试的全班各科成绩
   - AI分析：班级整体水平定位（与年级对比）、优势学科/薄弱学科识别、知识点掌握热力图、分层教学建议（尖子生/中等生/后进生各占比例及提升方向）
   - 输出：结构化的诊断报告，含数据图表 + AI文字分析

2. **学生个人学情画像**
   - 输入：学生历次考试成绩 + 成长档案数据
   - AI分析：学习趋势（上升/平稳/下滑）、学科强弱项、知识点漏洞、个性化学习建议
   - 输出：学生学情画像卡片，支持家长端查看

3. **试卷质量分析**
   - 输入：考试成绩分布 + 试卷题目信息
   - AI分析：难度系数评估、区分度分析、各题得分率、试题质量评价
   - 输出：试卷质量分析报告

**技术实现要点**：
- 后端组装好结构化的成绩数据（JSON格式），连同Prompt模板一起发给大模型
- AI返回的内容按预定义的结构解析（用JSON Schema约束输出格式），前端直接渲染
- 分析结果缓存到数据库，避免重复调用AI

#### 场景二：成长档案智能评语（P1）

**位置**：学生成长档案 → 学期评语

**功能描述**：

期末写评语是教师的一大负担。系统基于学生一学期的成绩、考勤、荣誉、技能、心理健康等数据，AI自动生成个性化评语初稿，教师修改确认后存入档案。

**具体能力**：

1. **学期评语自动生成**
   - 数据来源：各科成绩趋势、考勤记录、荣誉/技能记录、心理健康测评结果
   - AI生成：德智体美劳全面的评语，突出学生特点和进步点
   - 教师可以一键采纳、编辑修改、或重新生成

2. **综合素质评价**
   - 基于多维度数据自动生成五育（德智体美劳）雷达图
   - AI对每个维度给出文字描述和发展建议

**技术实现要点**：
- 评语生成Prompt需包含学生姓名、性别、班级等基本信息
- 支持教师选择评语风格（严谨型/鼓励型/简洁型）
- 生成记录存入数据库，保留版本历史

#### 场景三：OCR 智能成绩录入（P2）

**位置**：教学质量评估 → 成绩管理

**功能描述**：

教师上传试卷扫描件或Excel成绩表，系统自动识别并录入成绩，省去手动录入的繁琐。

**具体能力**：

1. **Excel成绩批量导入**
   - 上传Excel文件，自动识别列名（姓名、学号、各科分数）
   - 数据校验：重复学生、分数范围、缺失值检测
   - 确认后批量入库

2. **答题卡/OCR识别（进阶）**
   - 上传答题卡扫描件，OCR识别学生信息和客观题答案
   - 自动判分并生成成绩记录
   - （此功能技术复杂度较高，放在P2）

### 4.3 AI 能力统一封装

后端建立统一的 AI Service 层，所有AI相关调用走同一个入口：

```
backend-api/src/services/ai/
├── ai.service.js        # AI服务总入口（对外暴露的方法）
├── providers/           # AI提供商
│   ├── deepseek.js      # DeepSeek API封装
│   └── base.js          # 基类，便于后续扩展其他模型
├── prompts/             # Prompt模板管理
│   ├── teaching/
│   │   ├── classDiagnosis.js   # 班级学情诊断Prompt
│   │   └── studentProfile.js   # 学生学情画像Prompt
│   └── portfolio/
│       └── semesterComment.js  # 学期评语Prompt
└── utils/
    ├── tokenCounter.js  # Token计数
    └── cache.js         # 结果缓存
```

**统一封装的好处**：
- Prompt集中管理，便于调优和版本控制
- 换模型只需改provider，业务代码无感知
- 统一的限流、缓存、错误重试机制
- 调用日志统一记录，便于成本核算和问题排查

## 6. 技术升级建议

### 6.1 TypeScript 引入策略

**结论：后端暂缓，前端渐进式引入。**

**后端（Node.js + Express）：**
- 不建议立刻全量TS化。当前核心矛盾是架构分层不清，而不是类型安全
- 先完成三层架构重构，把代码结构理顺
- 重构完成后，可以考虑用 JSDoc + TypeScript 检查（`// @ts-check`）做轻量类型保障
- 如果团队TS经验丰富，也可以新模块直接用TS写，老模块逐步迁移

**前端（Vue 3）：**
- Vue 3 本身对TS支持很好，建议引入
- 但不追求"全量TS"，采用渐进式策略：
  - 第一步：`api/` 层和 `stores/` 层用TS（类型定义集中，收益最大）
  - 第二步：公共组件用TS，定义清晰的props类型
  - 第三步：业务页面逐步迁移，优先迁移核心模块
- 配合 Volar 插件获得完整的类型提示体验

### 6.2 代码质量保障

**ESLint + Prettier**
- 前后端都配置，统一代码风格
- 推荐规则集：
  - 前端：`eslint-plugin-vue` + `@vue/eslint-config-prettier`
  - 后端：`eslint:recommended`，如果用TS再加 `@typescript-eslint/recommended`

**Husky + lint-staged**
- 提交前自动 lint 和 format，确保入库代码质量
- 配置 commit-msg 钩子，规范 commit message 格式（Conventional Commits）

**代码规范文档**
- 写一份简短的团队代码规范（5-10页），涵盖命名、目录结构、注释要求、最佳实践
- 放在仓库根目录的 `docs/` 文件夹中

### 6.3 测试策略

**不追求高覆盖率，追求有效测试。**

当前测试覆盖率极低，从零开始建测试体系，优先级如下：

1. **单元测试：Service 层**
   - 后端 service 层是业务逻辑核心，最值得写单元测试
   - 重点测复杂计算逻辑（如成绩统计、分数段分析）
   - 工具函数（utils）100%覆盖
   - 工具：Jest

2. **接口测试：核心API**
   - P0模块的核心API做自动化接口测试
   - 覆盖正常流程 + 异常场景（参数错误、权限不足）
   - 工具：Supertest + Jest

3. **前端测试：组件测试（低优先级）**
   - 公共组件（DataTable、SearchForm等）做组件测试
   - 业务页面不做UI测试（维护成本太高）
   - 工具：Vue Test Utils + Vitest

4. **端到端测试：暂不引入**
   - 产品还在快速迭代期，E2E测试维护成本大于收益
   - V2.0以后产品稳定了再考虑

## 总结

这份规划的核心思路可以用三句话概括：

**做减法**：从9大模块砍到3个核心模块 + 3个辅助模块，聚焦"教学质量评估"这个差异化切入点。

**做深度**：AI不再是独立的聊天玩具，而是嵌入到学情分析、评语生成、成绩录入等具体场景中，用学校的真实数据驱动。

**做架构**：后端补服务层、前端补组件化和状态管理、数据库做精简和索引优化，先把地基打牢再往上盖楼。

移动端暂时放一放，把Web端做深做透，比两头都做但两头都浅要有价值得多。
