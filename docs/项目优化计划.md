## 二、本阶段的三条主线

进入现阶段后，继续堆功能的收益开始低于维护成本的上升。当前更值得处理的是三处结构性问题，它们直接决定后续开发的效率。

第一处是**数据迁移的载体**。迁移与种子原先全部以 JS 模块存在，业务变更要在 JS 里拼 SQL 字符串，阅读与评审都要先经过一层代码。现已全面转为 `.sql`。

第二处是**前端请求层分裂成两套**。一套带内联假数据（`api/index.js`），一套走真实接口（`api/request.js`），两者的响应格式还不一致（`{ success, data }` 与 `{ code, data }`），导致同一个后端字段变更要改多个组件。这是本阶段的改造重点。

第三处是**验证方式与项目节奏不匹配**。测试资产常驻仓库，但实际只在模块完成的那一刻有价值；现已改为「模块完成后一次性验证、验证后删除」。

与之并行的是两项业务完善：通知中心与数据看板，以及旧 AI 模块的清理与统一。

## 三、工程改造

### 3.1 迁移脚本全面 SQL 化（已完成）

迁移与种子已全部以 `.sql` 文件承载，版本号保持不变。`src/migrations` 目录现在只保留运行器与 `.sql` 文件，不再有业务 SQL 藏在 JS 字符串里。

**运行器改造**（`src/migrations/index.js`）

- 新增文件名解析，识别三种形式：

  ```
  V1.0.7_align_users_schema.up.sql     升级脚本
  V1.0.7_align_users_schema.down.sql   回滚脚本（可选）
  V0.0.1_init_users.js                 历史 JS 迁移（兼容保留）
  ```

- 同一版本号下 **SQL 优先于 JS**，读取文件文本后按语句执行（连接已开启 `multipleStatements`）。
- 迁移记录仍写入 `schema_migrations`，版本号取自文件名，历史版本转为 SQL 后与已执行记录一一对应，**现有数据库不受影响**。
- 新增 `src/migrations/runSql.js`：执行一次性 SQL 文件（种子、临时脚本），复用迁移器的自动建库连接，可 `npm run sql <file>` 直接调用。

**版本清单**

| 版本 | 内容 | 方向 |
|------|------|:----:|
| V0.0.1 | users 表 | up / down |
| V0.0.2 | 基础用户（admin/teacher1-2/student1-2，id 固定 1~5） | up / down |
| V1.0.0 | 核心表（学科/班级/考试/成绩/成长档案等） | up / down |
| V1.0.1 | users 补 class_id | up / down |
| V1.0.2 | AI 诊断报告表 | up / down |
| V1.0.3 | 课表条目表 | up / down |
| V1.0.4 | 活动报名表（并补齐 activities 的 cover / updated_at） | up / down |
| V1.0.5 | 选修课与选课记录表 | up / down |
| V1.0.6 | 操作日志表 | up / down |
| V1.0.7 | 对齐 users 结构（补齐 status） | up / down |

**幂等性实现**

MySQL 8 不支持 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`，纯 SQL 下改用 prepared statement 先探测再执行：

```sql
SET @exist := (SELECT COUNT(*) FROM information_schema.COLUMNS
               WHERE TABLE_SCHEMA = DATABASE()
                 AND TABLE_NAME = 'users'
                 AND COLUMN_NAME = 'status');
SET @ddl := IF(@exist > 0, 'DO 0',
  'ALTER TABLE users ADD COLUMN status TINYINT DEFAULT 1 AFTER avatar');
PREPARE stmt FROM @ddl; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

建表统一 `CREATE TABLE IF NOT EXISTS`，删表统一 `DROP TABLE IF EXISTS`，数据统一 `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE`，保证重复执行安全。

**种子脚本 SQL 化**

六个种子脚本（`seed_core_data`、`seed_test_users`、`seed_test_scores`、`seed_test_timetable`、`seed_test_activities`、`seed_test_electives`）已全部转为 `.sql`，原 JS 版本删除，`package.json` 改为经 `runSql.js` 调用：

```
npm run seed           # 按依赖顺序执行全部种子
npm run seed:core      # 学科/班级/考试/成绩/成长档案
npm run seed:users     # 8 位教师 + 50 位学生
npm run seed:scores    # 9 场考试的成绩与排名
npm run seed:timetable # 5 个班级一周课表
npm run seed:activities# 8 场活动 + 报名/签到
npm run seed:electives # 8 门选修课 + 选课
```

依赖顺序：`migrate → seed:core → seed:users → seed:scores/timetable/activities/electives`。

演示数据的随机性改为 SQL 内确定性算法（`CRC32` 哈希 + `ROW_NUMBER()` 抽样），重复执行结果完全一致，无需依赖 JS 运行时。

**本阶段修复的三个缺陷**

| 缺陷 | 现象 | 处理 |
|------|------|------|
| 回滚丢记录 | `V1.0.0.down.sql` 删除 `schema_migrations`，回滚后迁移记录丢失 | 移除该语句，改由运行器维护 |
| 空库缺列 | `initDatabase` 建表无 `status`，`V0.0.1` 为 `IF NOT EXISTS` 不生效，空库下 `User.js` 与种子报错 | 新增 `V1.0.7` 幂等补列 |
| 排序与抽样偏差 | 课表种子用户变量与列 collation 不一致报错；成绩种子只覆盖 4~9 场考试 | 变量显式 `COLLATE`；成绩补齐 1~9 场 |

**空库验证结果**

`init:db → migrate → seed` 全链路在全新数据库上通过，各表行数与现有库一致（users 59、subjects 13、classes 5、exams 9、exam_scores 900、timetable_entries 120、activity_registrations 370、elective_selections 204），种子重复执行结果不变。

### 3.2 前后端解耦（已完成）

前端原先有两套请求层并存。`api/index.js` 以对象字面量集中定义全部接口，内部以 `USE_MOCK = true` 返回大段内联假数据，成功响应形如 `{ success, data, message }`；`api/request.js` 是新架构的 axios 实例，成功响应形如 `{ code, data, message }`。十一个视图文件与 `stores/user.js` 仍在引用旧层，其中 `Services.vue`、`AIHealth*` 系列等依赖内联假数据。

视图因此同时承担了三件本不属于它的事：拼接接口路径、识别响应包装格式、映射后端字段名。任何一处后端字段调整都会外溢到多个组件。

改造分三层落地。

**请求层收敛为单一入口** `api/request.js`。响应拦截器把两种包装格式统一解包，成功时向调用方返回业务数据本身，失败时统一提示并 reject；401 的处理（清理登录态、跳转登录页）集中在这一层。视图只消费业务数据，不再判断 `code` 或 `success`。

**接口按业务域拆分为独立模块**，每个模块只暴露该域的操作。`elective.js`、`activity.js`、`timetable.js`、`teaching.js`、`portfolio.js`、`adminUsers.js`、`home.js`、`auth.js`、`courses.js`、`services.js`、`social.js`、`notifications.js`、`profile.js`、`aiHealth.js` 均为该形态，`api/index.js` 已删除，全部视图不再引用旧层。

**内联假数据从请求层移除**。需要演示数据时通过种子脚本写入数据库；确需前端 mock 的场景，放入独立的 `src/api/mock/` 目录并在开发环境按需引入，不与真实请求代码混写。

### 3.3 验证策略调整（已完成）

按「模块完成后验证、测试文件不保留」的节奏，已清理常驻测试资产：移除 `tests/` 目录（4 个测试套件）、`package.json` 中的 Jest 配置、`jest` / `supertest` 依赖与 `test` / `test:watch` 脚本。

后续每个模块完成时生成一次性验证脚本，覆盖该模块的核心接口与关键分支，运行通过后删除，不进入版本库。验证以真实请求为主，必要时配合临时单元测试。这样仓库里不残留与当前代码不同步的测试。

## 六、风险

| 风险 | 说明 | 应对 |
|------|------|------|
| 迁移 SQL 化的幂等性 | MySQL 不支持条件加列，历史迁移依赖 JS 辅助函数 | 条件 DDL 用 prepared statement；建删表统一带 IF EXISTS |
| 迁移记录错位 | 版本号一旦变动，已执行记录无法匹配 | 转换时严格保持 `Vx.x.x` 版本号不变（已完成） |
| 空库与存量库结构漂移 | 两条建表链路（initDatabase / V0.0.1）字段不一致 | 以迁移兜底对齐（`V1.0.7`），空库全链路验证 |
| 连接层与表 collation 不一致 | 用户变量与 `utf8mb4_unicode_ci` 列比较报错 | 变量显式 `COLLATE`；SQL 中避免变量直比列 |
| 请求层归一化的回归面 | 涉及十一个视图与 `stores/user.js` | 按视图逐个迁移并即时验证，完成后再删除旧层 |
| 旧模块误删 | 部分组件可能被其他页面复用 | 删除前做引用扫描，先下线路由与菜单，确认无引用后再删文件 |
| 推送与现有广播的冲突 | `socketHandler` 已有食堂人流的定时广播 | 通知使用独立频道，避免与现有广播共用命名空间 |
