## 一、本阶段的判断依据

上一阶段（v3.2）已完成迁移与种子 SQL 化、前后端请求层解耦、常驻测试资产清理、通知中心与数据看板收敛、旧 AI 模块下线。功能面已经够用，继续加功能的收益低于维护成本的上升。本阶段不动功能，只处理四类结构性问题。

判断来自一次全量代码体检，结论有三条。

第一条，文档与代码已经分叉。技术文档仍在描述 `.js` 迁移与 `seed_core_data.js`，而代码里早已是 `.sql`；README 的项目结构树、脚本清单、功能状态也都停留在旧版本。文档现在不是"略微滞后"，而是会误导新加入的人按错误的路径操作。

第二条，命名分裂已经固化成两套风格。后端路由有 8 个用 `.routes.js`、8 个不用；模型有 12 个用 `.model.js`、8 个不用；前端视图一半扁平、一半分目录。同一类文件出现两种命名，会让"按名字找文件"失效。

第三条，护栏覆盖不均。项目已经具备参数校验中间件、统一响应工具、统一错误处理、审计中间件，但只有一半的路由用上了它们，另一半仍在手写响应、直连数据库、缺少事务。这属于"能力已备、执行未齐"，补起来是收敛而非新建。

规模上，前后端共有 10 个视图超过 1000 行（`views/StudentHome.vue` 1808 行、`views/TeacherHome.vue` 1526 行、`views/AdminHome.vue` 1360 行、`views/teaching/StudentAnalysis.vue` 1464 行、`views/Services.vue` 1307 行、`views/teaching/ClassAnalysis.vue` 1157 行、`views/portfolio/PortfolioOverview.vue` 1114 行、`views/Learning.vue` 1096 行、`views/portfolio/MentalHealth.vue` 1093 行、`views/portfolio/CommentList.vue` 1010 行），后端 `services/teaching.service.js` 1763 行、`routes/aiHealth.js` 687 行。这些文件是"改一处要跳好几个文件"的主要来源。

## 二、优化原则与边界

### 2.1 可回归的定义

本计划把"可回归"落成三条可验证的约束，每一阶段结束时逐条核对：

接口契约不变。请求路径、方法、参数名、成功时的业务数据字段一律不动。允许调整的只有响应的信封格式，因为前端 `api/request.js` 的归一化层（第 29–40 行）已经同时兼容 `{code, data, message}` 与 `{success, data, message}`，并已回退支持裸数据，信封统一对页面不可见。

页面行为不变。路由路径、菜单项、权限角色、交互流程、展示字段保持原样。

数据不变。不新增、不删除、不改动任何表结构；重构涉及写操作时，最终落库结果与改造前一致。

### 2.2 本次不做的清单

| 不做 | 理由 |
|------|------|
| TypeScript 迁移 | 后端是 JS，混用反而乱；引入初期会拖慢改动速度 |
| 补 tests | 验证策略是"临时脚本用完即删"，保持这一选择 |
| CI/CD | 已明确不做 |
| Docker | 已明确不做 |
| mobile-app 相关 | 已明确不做 |
| 新增业务功能 | 已明确不做 |
| 引入状态管理重构 | Pinia 已在用，业务状态散落属可接受的技术债 |
| 换 ORM | 现在 model 层直接 SQL，够用；换 ORM 伤筋动骨 |
| 数据库表结构改动 | 迁移已稳定，不动 |

原 `docs/SmartCampus项目规划方案9.25.md` 的 6.1（TypeScript 引入策略）与 6.3（测试策略）曾与本清单直接冲突。该文件已由用户手动删除，冲突随之消除；阶段一需要确认 `README.md` 与 `docs/项目技术文档.md` 中不再残留指向该文件的链接或引用。

## 四、阶段二　命名与目录一致性

这一阶段只做移动与改名，不改任何逻辑。所有改动都是机械的，风险来自遗漏引用，因此每条改动都必须以全量引用扫描收尾。

后端模型：`PascalCase.model.js`。据此 `User.js` → `User.model.js`，其余 7 个同理。

## 五、阶段三　后端健壮性补强（只补护栏）

### 5.1 响应与错误出口统一

`utils/response.js` 已经提供了 `success`、`fail`、`paginate` 与错误码常量，但只有 9 个路由在用：`admin-users.routes.js`、`activity.routes.js`、`dashboard.routes.js`、`portfolio.routes.js`、`operation-log.routes.js`、`notification.routes.js`、`timetable.routes.js`、`elective.routes.js`、`teaching.routes.js`。

仍在手写 `{ success, data, message }` 的有 8 个：`auth.routes.js`、`user.routes.js`、`course.routes.js`、`service.routes.js`、`social.routes.js`、`ai-health.routes.js`、`ai-science.routes.js`，以及 `middleware/auth.js`（`verifyToken` 与 `checkRole` 的 401/403 响应，第 9、19、27、31 行）。

统一到 `{code, data, message}` 之后，前端无需任何改动，因为归一化层已同时兼容两种信封。这是本阶段收益最高、风险最低的一项。

### 5.2 写操作事务边界

以下四处写操作包含"先校验再写入"或"批量写 + 后续计算"，目前没有事务包裹，中途失败会留下不一致数据。

| 位置 | 现象 |
|------|------|
| `services/teaching.service.js` 第 584–687 行 | 成绩导入先批量插入再循环计算排名，排名失败会留下未排名的成绩 |
| `services/user.service.js` 第 344–516 行 | 批量导入用户逐条 `create` 后再分配班级，中途失败会留下半批数据 |
| `services/elective.service.js` 第 277–316 行 | 选课先校验名额再写入，并发下名额与选课记录可能不一致 |
| `services/activity.service.js` 第 175–200 行 | 活动报名先校验名额再写入，同上 |

做法是从连接池取连接、`beginTransaction` 包裹整段、成功 `commit`、失败 `rollback` 后抛出。并发下的名额竞争，用 `SELECT ... FOR UPDATE` 或条件更新（`WHERE selected_count < capacity`）在事务内解决，不引入新的业务规则。

### 5.3 SQL 参数化

`services/dashboard.service.js` 第 133–167、171–198、204–228 行把 `classIds.join(',')` 直接插进 `IN (...)`。虽然 `classIds` 来自库内查询、当前不构成注入，但这类拼接一旦被后续改动带进外部输入就是漏洞。改为按数量生成占位符、值走参数数组，与 `services/portfolio.service.js` 第 892、978 行的写法一致。

`routes/ai-health.routes.js` 第 231–267 行动态拼 `WHERE` 后再用 `LIMIT ? OFFSET ?`，需要确认拼进 `WHERE` 的值全部走参数绑定。`services/teaching.service.js` 第 1680–1685 行的 `LIMIT ${safeLimit}` 是已转数字的常量，属于可接受的 LIMIT 内联用法，保持不动。

### 5.4 路由层职责回归

三层架构的约定是路由只做鉴权、校验、调服务、返响应。以下三处把数据访问写进了路由。

`routes/ai-health.routes.js` 共 687 行，`/overview`（第 106–220 行）、`/students`（第 224–288 行）、`/warnings`（第 375–441 行）等直接访问数据库并做聚合计算。应把查询与统计下沉为 `services/aiHealth.service.js`，路由只保留参数处理与响应。

`routes/user.routes.js` 第 101–172 行的 dashboard 接口内联拼 SQL 并组装数据，应下沉到服务层。

`routes/course.routes.js` 第 7–21、25–40 行的学期与教师列表查询，应下沉到服务层。

下沉后各接口的输入输出保持不变，属于纯搬迁。

### 5.5 校验与鉴权护栏

`middleware/validate.js` 已具备必填、类型、区间、枚举、正则、默认值能力，但 `course.routes.js`、`user.routes.js`、`social.routes.js`、`service.routes.js` 的写接口未挂载它，直接使用 `req.body`。按接口逐个补 `validate({ body: {...} })`，规则取自当前代码里已有的隐式校验，不新增约束。

`routes/ai-science.routes.js` 第 10 行的 `/chat` 没有挂 `verifyToken`。全局 AI 助手挂载在需要登录的 `MainLayout` 上，补上鉴权不会影响正常使用，但会拦住未登录直连，属于应补的护栏。

### 5.6 边界与敏感信息

分页参数多处直接 `parseInt` 后使用（`course.routes.js` 第 45–46 行、`social.routes.js` 第 9–10 行、`service.routes.js` 第 44–45 行、`ai-health.routes.js` 第 227–229 行），缺少 NaN 拦截与上限。统一在 `validate` 的 `query` 规则里给 `page`/`pageSize` 设 `min: 1`、`max: 200`，非整数由 `coerce` 拦截。

`middleware/errorHandler.js` 第 48–55 行在开发环境返回 `error` 与 `stack`，改为只在 `NODE_ENV=development` 且显式开启调试开关时返回。

`routes/ai-health.routes.js` 第 291–371 行的学生详情返回 `email`、`phone`，按调用者角色返回最小必要字段。

`src/app.js` 第 33、39 行的 CORS 与 WebSocket 均允许 `*`，改为从环境变量读取允许来源，开发环境保留宽松默认。

`auditLog` 依赖 `res.locals.targetType` 记录审计目标，`ai-health.routes.js` 多数写接口未设置。补齐全量写操作的该字段。

### 5.7 任务与验收

任务按 5.1 至 5.6 分组执行，建议顺序为：响应统一 → 校验与鉴权补齐 → 事务 → SQL 参数化 → 职责下沉 → 边界与敏感信息。每组结束后重启后端并跑一次接口冒烟。

验收以行为比对为准：对改造前后的同一批接口，用相同入参发请求，成功响应的业务数据（`data` 内容）逐字段一致；失败路径的错误码与提示保持同类语义；写操作在模拟中途失败时能完整回滚。

## 六、阶段四　前端可维护性补强

目标是把"改一个业务模块要在 5 个文件间跳转"降到"改动集中在一个目录内"。

### 6.1 跳转链路的成因

以成绩管理为例，一次字段调整要经过：`views/teaching/ScoreList.vue`（表格列、表单项）→ `api/teaching.js`（接口封装）→ 后端路由与响应字段。以班级管理为例，还要额外经过 `composables/useTable.js`、`composables/useDialog.js`、`components/common/SearchForm.vue`、`components/common/DataTable.vue`，因为列定义、搜索项、弹窗表单分散在这些通用件里。以学生首页为例，链路是 `views/home/StudentHome.vue` → `api/home.js` → `stores/user.js` → `stores/socket.js` → `components/AIAssistantFloat.vue`。

成因有两个：一是页面把"数据请求、业务计算、图表配置、模板、样式"全部收在一个 `.vue` 里，文件大到无法一眼定位；二是本该属于某个业务域的配置（列定义、表单项、图表 option）被放进了跨域共享的通用件，改 A 域要动共享文件，容易碰到 B 域。

### 6.2 目标结构：按业务域内聚

每个业务域一个目录，域内的页面、局部组件、局部组合式函数、列与表单配置都放在一起，只有真正的跨域能力才留在 `components/common/` 与 `composables/`。

```
views/teaching/
├── ScoreList.vue           页面：只做编排
├── components/
│   ├── ScoreTable.vue      该域的表格与列定义
│   └── ScoreFormDialog.vue 该域的表单弹窗
└── useScorePage.js         该域的数据加载与业务计算
```

判断标准很简单：一个业务域的改动，若需要修改 `views/<domain>/` 之外的共享文件，说明该处抽象放错了位置。

### 6.3 大组件拆分

对 6 个超过 1000 行的核心页面做拆分，拆分只移动代码、不改行为。

`views/home/StudentHome.vue`（1808 行）、`views/home/TeacherHome.vue`（1526 行）、`views/home/AdminHome.vue`（1360 行）按"统计区 / 通知区 / 入口区 / 个人卡片"拆为局部子组件，数据加载与派生计算抽成域内组合式函数。

`views/teaching/StudentAnalysis.vue`（1464 行）、`views/teaching/ClassAnalysis.vue`（1157 行）按"数据请求 / 分数段与排名计算 / ECharts 配置 / 列表区"拆开，其中分数段统计与排名计算是纯函数，抽成独立模块后可单独阅读；ECharts 配置抽成域内 `use*Chart.js`。

`views/portfolio/PortfolioOverview.vue`（1114 行）、`views/portfolio/MentalHealth.vue`（1093 行）、`views/portfolio/CommentList.vue`（1010 行）按"列表区 / 图表区 / 筛选区 / 弹窗区"拆开。

`components/AIAssistant.vue`（1140 行）、`components/CourseInteraction.vue`（1046 行）、`components/LearningResources.vue`（757 行）按功能块拆分，其中 `CourseInteraction.vue` 与 `LearningResources.vue` 只被 `views/course/Courses.vue` 使用，应一并下沉为该域的局部组件。

### 6.4 复用收敛

`composables/useTable.js` 与 `useDialog.js` 已在 `views/system/Users.vue`、`ExamList.vue`、`ClassManage.vue`、`SubjectManage.vue`、`ScoreList.vue`、`SkillList.vue`、`HonorList.vue`、`CommentList.vue`、`MentalHealth.vue` 中使用，但 `views/home/StudentHome.vue`、`views/home/TeacherHome.vue`、`views/home/AdminHome.vue`、`views/course/Courses.vue`、`views/student/Growth.vue`、`views/student/Learning.vue`、`views/home/AIHealthOverview.vue`、`views/home/AIHealthAnalytics.vue` 仍各自实现列表、分页、搜索、弹窗逻辑。把这些页面统一到已有的 `useTable` / `useDialog` 上，减少同一套逻辑的多份实现。

`composables/useECharts.js` 已被教学分析与档案页使用，但图表 option 仍内联在页面里。把 option 构造抽成域内纯函数，页面只负责把数据传进去。

### 6.5 任务与验收

任务是先做 6.2 的结构调整（与阶段二的目录归并一起做），再做 6.3 的拆分，最后做 6.4 的复用收敛。

验收方式是构建与页面比对：`npm run build` 通过；对每个被拆分的页面，逐页核对路由可达、权限生效、数据加载正常、图表渲染正常、弹窗增删改查正常、分页与筛选正常。拆分前后页面的可见行为与网络请求序列一致。

## 八、回归验证方式

延续项目既定的"模块完成后一次性验证、验证后删除"策略，不引入常驻测试资产。

每个阶段收尾时生成一次性冒烟脚本，覆盖该阶段触及的接口与页面，运行通过后删除。后端以真实请求为主：登录拿 token，逐个调用被改动模块的接口，比对改造前后的 `data` 字段。前端以构建 + 手动页面走查为主，必要时用浏览器逐页核对。

阶段三的验证重点是失败路径：对每个补了事务的写操作，人为制造中途失败（如临时让排名计算抛错），确认数据完整回滚。

## 九、风险与应对

| 风险 | 说明 | 应对 |
|------|------|------|
| 改名遗漏引用 | 模型与服务被大量 `require`，漏改会运行时报错 | 每个改名文件用 `rg` 做旧名残留扫描；后端启动一次并跑冒烟 |
| 前端目录归并破坏路由 | 视图移动后 `router/index.js` 的动态 import 与组件相对引用会失效 | 移动与改引用在同一批次完成，改完立即 `npm run build` |
| 响应格式统一的回归面 | 涉及 8 个路由与鉴权中间件 | 前端归一化层已兼容两种信封；逐接口比对 `data` 字段 |
| 事务改造改变并发行为 | 加锁或条件更新可能改变高并发下的失败表现 | 事务只包裹已有逻辑，不加新规则；对名额竞争场景做并发验证 |
| 职责下沉引入行为偏差 | `aiHealth.js` 等搬迁面较大 | 只移动代码不改逻辑；搬迁前后用相同入参比对响应 |
| 大组件拆分破坏页面 | 首页三件套与教学分析页交互复杂 | 按可见行为逐页核对；拆分粒度以"一个区块一个子组件"为限 |
| 文档再次漂移 | 文档更新后代码继续演进 | 阶段一为每类事实指定唯一出处，重复描述改为引用 |
